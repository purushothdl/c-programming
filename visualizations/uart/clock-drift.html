No shared clock. So how does the receiver stay in step?

The receiver times every bit with its own clock. If that clock is a little off, the sample point slides across the bit. It restarts on every start bit, so the slide only has 10 bits to add up. Drag the error and watch where the samples land.

01 · error budget

Does your baud rate fit?

The divider is a whole number, so the chip cannot hit every baud rate exactly. Pick a row. Then set how far off the other side is (the PC's USB-serial chip). Both errors share one budget.

Budget from RM0390 Tables 160 and 161 (p. 797) for 8 data bits, OVER8 = 0, ONEBIT = 0: 3.75 % when the fraction is 0, 3.33 % when it is not. It covers both ends and the line together. This chip runs from the 16 MHz HSI, an internal RC oscillator and not a crystal. Its own accuracy (datasheet Table 41, p. 106) eats into the same budget, so the slider matters even at 115200.

02 · where each sample lands

One frame, ten bits

A frame is a start bit (0), 8 data bits (LSB first) and a stop bit (1). The receiver finds the start edge, then samples the middle of each bit: ticks 8, 9 and 10 of 16 (RM0390 p. 783 and 785). Dots show the 9th sample. Dot colour: green = in the right bit, red = in a neighbour, amber = the three samples disagree.

03 · easy to get wrong

Gotchas

Errors add upTransmitter, receiver, divider rounding and the line all share the same 3.33 %.
Fast baud rates round badlyAt 16 MHz, 921600 needs BRR 17.36 and gets 17: +2.12 %. That alone uses 64 % of the budget.
The start bit is the resetEach frame restarts the count, so drift only builds over 10 bits, not over the whole message.
The stop bit is the last to be sampledIt is the farthest from the start edge, so it fails first. A wrong stop bit shows up as a framing error.
OVER8 = 1 shrinks the budgetRM0390 Table 161: 2 % instead of 3.33 %. The program keeps OVER8 = 0.
Changing BRR mid-messageThe baud counters update right after a write to BRR. Set it before the UART is enabled, as uart_init does.
