The bytes keep coming. The loop is asleep.

A byte arrives every 87 µs. This loop looks at the USART once every millisecond, so eleven bytes queue up behind one register. The hardware keeps the first and throws the rest away. The ! on screen is the only trace.

01 · who talks to whom

One millisecond, one look

The first tab is the real program at 115200. The second runs the same code at 9600, where it happens to work. The third is a bug tab: it never finishes the sequence that clears ORE.

Why the ring fixes it uart/ring-buffer.html

Turn on RXNEIE and the USART interrupts on the first byte of a burst. The handler reads DR within a few microseconds, long before the next byte completes, so ORE never sets. main then drains a ring at its own pace, and nothing is dropped while it prints.

What this loop can never do ceiling

One look per millisecond is at most 1 000 bytes per second. The wire delivers 11 511. Speeding up the loop body does not help while the sleep is there; the sleep is the design.

Human typing hides the bug: keystrokes are ~100 ms apart, so each one is read safely. Paste a line and the failures appear.

02 · sample data · simplified model

When does the look become too slow?

Nineteen bytes arrive back to back. Drag the look interval and change the baud. A byte survives only if the loop looks at it before the next one completes.

03 · the numbers

Baud, BRR, byte time

The program runs on the 16 MHz HSI reset clock; it never starts the PLL. BRR is fCK ÷ baud rounded, because USARTDIV is coded in sixteenths (RM0390 p. 788).

04 · easy to get wrong

Gotchas

ORE needs both readsReading SR alone does not clear it. The sequence is SR read, then DR read (RM0390 p. 815).
ORE without RXNE is realA byte can be lost exactly when the previous one is read, leaving ORE set with nothing to read. Read DR anyway, to finish the clear.
RDR keeps the first byteWhile RXNE is set, new bytes overwrite the shift register, not RDR. So the byte you read is the oldest one (RM0390 p. 784).
One ! is not one lost byteThe flag says at least one byte was lost. It cannot count them; this program can only mark where the gap ended.
The sleep is the bottleneckAt 115200 the loop must look faster than one byte, 86.9 µs, to lose nothing. A 1 ms sleep is eleven bytes too slow.
Slow typing hides itKeystrokes are far apart. Only a pasted line or a fast sender fills the gap between looks.
