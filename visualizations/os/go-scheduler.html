Go runtime · src/runtime/proc.go

Thousands of goroutines, a handful of threads. The runtime does the juggling.

A goroutine is a small struct, not a thread. A few OS threads run them, and the runtime moves goroutines between threads in user space. The kernel only gets involved when a thread has to sleep or wake.

G · goroutineYour function plus its own small stack. Cheap to make, and thousands can exist at once.
M · machineA real OS thread. The kernel schedules it. It can sleep inside a system call.
P · processorA permit to run Go code, with a queue of runnable Gs. An M needs a P to run a G. There are GOMAXPROCS of them.

What a switch costs

Same job, two ways: hand the CPU to another goroutine, or to another thread. This sequence has no Watch table and no code sheet, only the steps.

About 64 times apart. The thread number includes waking a sleeping thread, not only the context switch. Your machine will give other numbers, but the gap is the point.

The test ping-pong over two unbuffered channels

a, b := make(chan int), make(chan int)
go func() { for i := 0; i < n; i++ { <-a; b <- i } }()
for i := 0; i < n; i++ { a <- i; <-b }
// 1 P: both goroutines share a thread.
// Locked: runtime.LockOSThread() in both, 4 Ps.
// ns per switch = elapsed / n / 2
03 · easy to get wrong

Gotchas

go f() does not run f nowThe new goroutine waits in the current P's runnext slot. Another thread only takes it after a short pause (runqgrab, about 3 µs).
A blocking call does not block other goroutinesThe thread sleeps, but sysmon takes its P away and gives it to another thread. In my test 1.19 million loops ran in 50 ms with one P.
A tight loop can hold a P for 10 ms or morePreemption is by time slice, checked by sysmon. In my run the other goroutine waited 13 ms, not 1.
Ping-pong pairs cannot starve the rest foreverrunnext shares one time slice, so sysmon preempts the pair after 10 ms (comment in runqput). The global queue is also checked every 61 ticks.
Steals take the front of the queueThe thief takes half, rounded up (n - n/2), so 4 queued goroutines become 2 and 2.
LockOSThread brings thread costs backA goroutine pinned to a thread switches at thread cost, as the measured card shows.
